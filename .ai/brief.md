# 生活予定・支出統合アプリ プロダクト仕様（MVP）

> この文書は「何を作るか」を定義する。設計・技術選定・実装方式は開発エージェントに委ねる。
> 「未決定事項」に挙げた項目は、ユーザーの確認なしに確定仕様として扱わないこと。

---

## 1. 一言で

予定とお金を一緒に見られる。記録は写真を撮るだけ。家計を細かく管理することをユーザーに求めない、長く使える生活カレンダー。

コンセプト：**「未来の予定と、未来のお金を管理するアプリ」**

## 2. 守るべき原則（全仕様に優先する）

1. **記録は「撮影して取り込む」だけで完結すること。** 手入力は補助手段とする。
2. **分類させない。** カテゴリ、費目、予算、支出の評価は持たない。支出の意味付けはユーザーに委ねる。
3. **予定とお金を同じ時間軸で見せる。** 過去の実績、未来の予定支出、定期項目を1つのカレンダーに表示する。
4. **既存のGoogleカレンダー環境を尊重する。** 予定の二重入力をさせない。お金の情報をユーザーのカレンダーに書き込まない。
5. **確認や管理の作業を増やさない。** 通知、ゲーミフィケーション、操作を妨げる広告は入れない。
6. **重い連携に手を広げない。** 銀行APIやカード連携は扱わない。
7. **シンプルさを損なう機能は追加しない。**

## 3. 対象プラットフォーム

- iOSとAndroidで**同時にリリース**する。
- 両OSとも、オフラインで基本機能がすべて動くこと。データは端末内に保存する。
- 技術スタックは開発エージェントが選定する。参考：
  - 要件の中心は、独自描画の月表示カレンダー、端末カレンダーの読み取り、日本語OCR。
  - クロスプラットフォームの候補はFlutterとReact Native（Expo）。どちらでも、端末カレンダーの読み取りとGoogle ML Kitによる日本語OCRは実現できることを確認済み。

## 4. 中心となる概念

### 4.1 お金の記録（エントリ）

すべてのお金の情報は、次の項目を持つ1種類のエントリとして扱う。

| 項目 | 必須 | 内容 |
|---|---|---|
| 金額 | ○ | 正の整数（円） |
| 種別 | ○ | 支出 / 収入 |
| 日付 | ○ | 初期値は今日 |
| 利用先・内容 | − | 店名や、「家賃」「副業」などの自由入力。分類は持たない |
| 状態 | ○ | 実績 / 予定（日付から自動で決まる。下記参照） |
| 発生元 | ○ | 画像取り込み / 手入力 / 定期項目 / 単発の予定 |
| 画像 | − | 取り込んだレシートやスクリーンショット |
| メモ | − | 任意 |

**状態のルール**
- 日付が今日以前なら**実績**、未来なら**予定**とする。
- 予定のエントリも定期項目の回も、**当日を過ぎたら自動で実績として扱う。** 「支払い済み」の確認操作は求めない。

### 4.2 定期項目（収入・支出共通）

家賃、サブスク、ローン、保険、携帯料金、給与、副業収入、ボーナスなどを事前に登録する。

**周期の種類**

| 種類 | 例 | 設定項目 |
|---|---|---|
| 毎週 | 習い事 | 曜日 |
| 隔週 | 隔週払いのバイト代 | 曜日と起点日 |
| 毎月 | 家賃、給与、サブスク | 日付（「月末」も選択可） |
| Nヶ月ごと | 2ヶ月ごとの水道代、半年ごとの保険 | 間隔（N）、起点月、日付 |
| 毎年 | 年会費、自動車税 | 月と日 |
| 月を指定 | ボーナス（6月・12月） | 対象の月（複数選択可）と日付 |

共通の設定項目：名前（自由入力）、種別（支出/収入）、目安金額、開始日、終了日（任意）

**日付のルール**
- 指定した日がその月にない場合（31日指定の2月など）は、その月の末日にする。
- 土日祝による支払い日の調整は**未決定**（7章参照）。

**金額と編集のルール**
- 定期項目は**テンプレート**であり、金額は**あくまで目安**とする。
- **各回の金額は、それぞれ独立して修正できる。**
- 各回は1回だけスキップできる（請求がなかった月など）。
- テンプレートの金額や内容を変えても、**すでに修正またはスキップした回と過去の回は変わらない。** 反映されるのは、未修正の未来の回だけ。
- 定期項目を削除する場合は、過去の実績を残すか一緒に消すかをユーザーが選べること。

**実装方針（推奨）**
- 未来の回は、周期のルールから表示時に計算する。データとして保存するのは「修正した回」と「スキップした回」だけにする。
- これで上記の編集ルールが自然に成り立ち、データ量も増えない。

### 4.3 単発の予定（予定支出・予定収入）

- 定期ではない未来のお金を登録できる。例：忘年会で5,000円くらい、給付金の入金予定。
- 入力は金額・日付・内容だけ。
- **カレンダーの予定に金額を添える**使い方を想定する。端末カレンダーの予定を選んで「この予定でかかりそうな金額」を付けられること。紐づけはアプリ内で持ち、元のカレンダー側には書き込まない。
- 入力は任意で、使わなくても他の機能に影響しないこと。

### 4.4 カレンダーの予定

- 端末の標準カレンダー経由で、Googleカレンダーなどの予定を**読み取って表示する**（MVPは読み取りのみ）。
- 表示するカレンダーをユーザーが選べること。
- 予定の作成・編集は、OS標準のカレンダー画面に任せる。アプリから標準カレンダーの作成画面を開くのは可。
- 将来、Google Calendar APIとの直接連携を追加できるよう、予定を取得する部分は差し替えられる作りにする。

## 5. 機能仕様

### 5.1 画像取り込み（最重要機能）

**対象**
- 紙のレシートの撮影
- 写真アプリからの画像の選択（**複数枚をまとめて**選べること）
- **決済画面やネット通販の注文確認画面のスクリーンショット**（QR決済、EC。紙のレシートが出ない支払いへの対応）

**OCRで取得する項目**
- 合計金額
- 日付
- 店名・利用先

明細の解析、商品の分類、税率別の集計は行わない。

**処理**
- 端末内で処理する。画像をサーバーに送らない。
- 日本語のレシートに合わせた抽出ロジックを用意する（「合計」というキーワード、日付の書式、上部の行から店名を推定する、など）。
- 読み取れなかった項目は空欄にし、金額が読めない場合も保存はできるようにする。

**取り込み後のUX**
- 撮影すると、金額・日付・店名を入力済みの**確認カード**が出る。
- 内容が正しければ**「保存」を1タップ**で完了する。
- 修正する場合は、その場で項目をタップして直す。画面遷移は増やさない。
- まとめて取り込んだ場合は、確認カードを順に送れる。

### 5.2 手入力

- 必須は金額だけ。日付は今日、種別は支出を初期値にする。
- 店名やメモは任意。
- カレンダーの日付から直接入力を始められること（その日付が入った状態で開く）。

### 5.3 カレンダー表示（メイン画面）

**月表示**
- 各日に予定の有無とその日の支出合計を表示する。収入がある日は収入も区別して表示する。
- 未来の予定支出・予定収入は、薄い色や枠線などで**実績と見分けられる**ようにする。
- 前後の月へスワイプで移動できる。

**日の詳細**（日付をタップ）
- その日のカレンダーの予定と、お金のエントリ（実績・予定・定期の回）を一覧で表示する。
- 各エントリを編集できる。定期項目の回は「この回だけ修正 / スキップ」を選べる。
- その日のエントリを追加できる。

**月のサマリー**（月表示の上部など）
- 今月の支出（実績）
- この先の予定支出（今月の残り）
- 今月の予定収入
- 予算、比較、良し悪しの評価、グラフは**出さない**。

### 5.4 定期項目の管理

- 登録済みの定期項目の一覧（名前、周期、目安金額、次回の日付）
- 追加、編集、終了、削除
- 一覧から各回の履歴を確認できる。

### 5.5 データの書き出し

- お金のエントリをCSVで書き出せる（**無料**）。
- 列：日付、種別、金額、利用先・内容、状態、発生元、メモ

### 5.6 画像の保存と削除

- 取り込んだ画像は端末内にだけ保存する。
- 設定で「OCR後に画像を自動削除する」を選べる。
- エントリを削除したら、そのエントリの画像も削除する。

### 5.7 設定

- 表示するカレンダーの選択
- 画像の自動削除
- 週の始まり（日曜 / 月曜）
- CSVの書き出し

## 6. MVPに含めないもの

| 項目 | 扱い |
|---|---|
| Google Calendar APIとの直接連携 | 将来。MVPは端末カレンダー経由 |
| 予定の作成・編集をアプリ内で行う | 将来検討 |
| クラウドバックアップ、端末間の同期 | 将来の有料化候補 |
| 残額の予測（開始残高からの推移） | 将来の拡張。開始残高を後から追加できるデータ構造にしておく |
| 通知 | 入れない |
| カテゴリ、予算、支出の評価、グラフ分析 | 入れない（コンセプトに反する） |
| 銀行・カードの自動連携 | 入れない |
| 商品明細の解析 | 入れない |
| 家族での共有 | 入れない |
| OCRのクラウド補助 | 端末内OCRの精度を見てから検討 |

**クレジットカードの扱い（決定事項）**
- 支出は**使った日に記録する**方式に統一する。
- カードの引き落としは定期項目として登録しないよう、定期項目の登録画面などで短く案内する。二重計上を避けるため。

| 支払い日が土日祝の場合の調整 | 「前の平日に前倒し」（給与向け）、「翌営業日」（口座振替向け）を定期項目ごとに選べるようにするか。MVPに入れるか未定 |
| 技術スタック | 開発エージェントが選定する（3章参照） |
| アプリ名・ブランド | 未定 |
| 無料 / 有料の境界と料金 | 方針：日常の基本機能は無料。クラウドバックアップ、端末間の同期、追加の便利機能を有料化の候補とする。詳細は未定 |
| データ移行（機種変更時） | MVPはCSVでの書き出しのみ。復元・移行の方式は未定 |
| 開発のロードマップ | 未定 |

## 8. 品質と事業面の方針

- 長く使われることを最優先する。継続率、保守性、運用コストの低さ、データの適切な扱いを重視する（将来のM&Aも視野に入れる）。
- 個人データ（支出、画像、予定）は端末の外に出さない。必要な権限（カレンダー、カメラ、写真）は、使う時点で理由を示して求める。
- OCRの精度は、実際の日本のレシートやスクリーンショットを集めたサンプルで計測できるようにしておく。
