# 開発ロードマップ

段階（M）ごとに、入れる FR・目的・依存・受け入れ条件を定める。M1 は MVP で、範囲は `mvp.md` の「M1 に入れる FR」と
同じ。FR の番号は `requirements.md`。持ち越しと未確定は `gaps.md`。流れの図は `diagrams/roadmap.md`。

段階を 3 つに分ける [assumed]。理由: 構想は FR-001〜FR-038 をすべて MVP に書いている（`mvp.md` の「M1 に入れない
FR」は「なし」）。MVP の後に残るのは、構想の「未決定事項」（`brief.md` 7）のうち MVP の後に検討すると決めたものと、
構想の「MVPに含めないもの」（`brief.md` 6）で「将来」とした項目だけなので、検討（M2）と拡張（M3）に分ける。
M2・M3 に入る FR はまだない。M2・M3 の要件は、その M の検討で `requirements.md` に FR として足し、この節の行に書く。

## M ごとの FR

- M1: FR-001〜FR-038
- M2: なし
- M3: なし

## M1 — MVP

### 目的

構想の MVP を iOS と Android の両方で、ネットワークなしで動かす（`mvp.md` の「最初に通す一連の流れ」）。
NFR-001〜NFR-018 は、すべて M1 で守る（`mvp.md` の「非機能要件」）。

### 依存

- 前の段階: なし（最初の段階）
- 着手の前に要る設計文書 [assumed]: `architecture.md`（技術スタックと選んだ理由の ADR）・`db.md`（エントリ・定期項目・
  修正した回とスキップした回の保存。NFR-011・NFR-013・NFR-017）・`security.md`（権限と端末内の保存。NFR-004〜NFR-008）・
  `environment.md`（両 OS の開発・検証環境）・`tests/test-plan.md`（FR ごとの受け入れ確認）
- 上の設計文書の設計のレビューが `reviews/NNNN-<題>.md`（置き場所と中身は `README.md`）にあり、重大・中の指摘の
  すべてに「直した」か、直さない理由が書いてある

### 受け入れ条件

M1 は MVP なので、`mvp.md` の「M1 の完了の目安」をファイルで確かめられる形にしたもの。

- `tests/test-plan.md` に、FR-001〜FR-038 のそれぞれの受け入れ確認の行がある。各行に「自動」か「手」の別があり、
  「手」の行には自動にできない理由が書いてある
- 「自動」の受け入れ確認のテストが `sh scripts/check.sh` から動き、`sh scripts/check.sh` が通る
- 「手」の受け入れ確認のすべてについて、確かめた日・OS・結果が `report.md` の「動作確認」の節にある
- `report.md` の「動作確認」の節に、「最初に通す一連の流れ」を iOS と Android の両方でネットワークなしで最後まで
  通した記録がある（NFR-001・NFR-002）
- `report.md` の「動作確認」の節に、OCR の精度（NFR-014・NFR-015）と、NFR-009・NFR-010 の時間の計測の結果がある。
  精度の目標の値は条件に含めない
- `deploy/readiness.md` があり、両 OS で公開できる状態までの手順が書いてある。ストアへの公開とデプロイは条件に含めない
- `requirements.md` の「未決定事項」の「技術スタック」の行が「決定。」で始まり、ADR を指している（G-001）
- `gaps.md` に、向かう M が M1 で仕分けが「今決める」の行が残っていない

## M2 — MVP の後の検討

### 目的

MVP で入れないと決めた構想の「未決定事項」を検討し、入れるものを要件にする [assumed]: 土日祝の支払い日の調整
（OQ-003・YOH-005）、無料 / 有料の境界と料金（OQ-004・YOH-006）、機種変更時のデータ移行、アプリ名・ブランド。

### 依存

- 前の段階: M1 の受け入れ条件をすべて満たしている
- 着手の前に要る設計文書: `report.md` の「既知の問題」と「未実装」の節・`gaps.md` の M2 向けの行。データ移行は `db.md` の
  保存の形式、課金は `security.md` にかかわるので、入れると決めたものから両文書を直す

### 受け入れ条件

- `gaps.md` に、向かう M が M2 の行が残っていない（決めた行は `gaps.md` の決まりで消してある）
- G-003〜G-006 に当たる `requirements.md` の「未決定事項」の行（アプリ名・土日祝の調整・料金・データ移行）が、
  その節の決まりで「決定。」か「入れない。」（どの M にも入れない）で始まり、決めた内容と、決めた先の FR・ADR・文書を
  指している。「未決定。」で始まる行（MVP にだけ入れないと決めた行も含む）が残っていない
- 入れると決めたものが `requirements.md` に FR として足してあり、この文書の「M2:」の行にその番号がある
- 前の決定を変えたものに ADR がある
- `sh scripts/check.sh` が通る

## M3 — 将来の拡張

### 目的

構想の「MVPに含めないもの」（`brief.md` 6）で「将来」「将来検討」「将来の有料化候補」とした項目を検討する [assumed]:
Google Calendar API との直接連携（NFR-012）、アプリ内での予定の作成・編集、クラウドバックアップと端末間の同期、
残額の予測（NFR-013）、OCR のクラウド補助。「入れない」とした項目（通知・カテゴリ・銀行連携など）は M3 にも入れない。

### 依存

- 前の段階: M2 の受け入れ条件をすべて満たしている（課金の境界がクラウドバックアップの扱いを決めるため）
- 着手の前に要る設計文書: `architecture.md`（差し替えられる予定の取得。NFR-012）・`db.md`（開始残高。NFR-013）・
  `security.md`（端末の外にデータを出すものは NFR-004 と NFR-007 の見直し）

### 受け入れ条件

- `gaps.md` に、向かう M が M3 の行が残っていない
- G-007〜G-011 に当たる `requirements.md` の「範囲外」の行に、入れるなら FR の番号が、入れないなら理由が書いてある
- 入れると決めたものが `requirements.md` に FR として足してあり、この文書の「M3:」の行にその番号がある
- 端末の外にデータを出すものには、`security.md` の見直しと ADR がある
- `sh scripts/check.sh` が通る
