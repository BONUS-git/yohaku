# プロダクト要求仕様書

構想（`brief.md`）から「何を作るか」を定める。設計・技術選定・実装方式は扱わない（`architecture.md` と ADR で決める）。

- 区分: `[explicit]` 構想にある／`[inferred]` 構想から読み取った／`[assumed]` 仮に置いた既定。各要求に 1 つだけ付ける
- 根拠: `[explicit]` の要求は、根拠の `brief.md` の節を「`brief.md` 節番号 節の名前」で書く
- 構想の「未決定事項」に当たる点は、決めるまで要件の前提にしない。扱いと決めた先は「未決定事項」の節に書く

## 目的と利用者

**目的**: 予定とお金を同じカレンダーで見られる、長く使える生活カレンダーを作る。記録は写真を撮るだけで済み、
家計を細かく管理することを求めない。コンセプトは「未来の予定と、未来のお金を管理するアプリ」。
（`brief.md` 1 一言で）

**利用者**: 予定を Google カレンダーなどの端末のカレンダーで管理していて、これからの支払いと収入を予定と
一緒に見たい個人。カテゴリ分けや予算管理はしたくない人。（`brief.md` 1 一言で・2 守るべき原則から読み取った）

**全体に優先する原則**（`brief.md` 2 守るべき原則）: 記録は撮影して取り込むだけで完結する（手入力は補助）。
分類させない。予定とお金を同じ時間軸で見せる。既存のカレンダー環境を尊重する。確認や管理の作業を増やさない。
重い連携に手を広げない。シンプルさを損なう機能は足さない。要求どうしが衝突するときは、この原則を優先する。

## 未決定事項

`brief.md` 7 未決定事項（ユーザーの確認が必要）の項目。どの要件も、未決定の項目の答えを前提にしない。
行の「扱い」は次のどれかで書く（`scripts/check_requirements.sh` が確かめる）:

- 決めていない: 「未決定」で始める
- MVP にだけ入れないと決めた（MVP の後の扱いは決めていない）: 「未決定。」で始め、MVP に入れないことと出どころの OQ を同じ行に書く
- 決めた: 「決定。」で始め、決めた内容と、それを書いた FR・ADR・文書（バッククォートのパス）を書く
- どの M にも入れないと決めた: 「入れない。」で始め、理由を書いた ADR か文書を指す

今の「支払い日が土日祝の場合の調整」（OQ-003）と「無料 / 有料の境界と料金」（OQ-004）の行は、MVP にだけ入れないと決めたものなので「未決定。」で始める。

| 項目 | 扱い |
|------|------|
| 支払い日が土日祝の場合の調整 | 未決定。MVP には入れない（OQ-003）。定期項目ごとに選べるようにするかと方式は、MVP の後に検討する（YOH-005） |
| 技術スタック | 未決定。開発エージェントが選定する（`architecture.md` と ADR で決める） |

| データ移行（機種変更時） | 未決定。MVP にあるのは CSV の書き出し（FR-036）だけで、復元・移行の方式は決めない |
| 開発のロードマップ | 決定。M ごとの FR・依存・受け入れ条件は `roadmap.md`（M1 は FR-001〜FR-038）。持ち越しは `gaps.md` |
